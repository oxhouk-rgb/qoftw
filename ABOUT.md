# ABOUT THE GAME — полный контекст проекта для разработчика / LLM

> Этот файл — «карта сознания» проекта. Его цель: любой новый читатель (человек или LLM),
> прочитав его один раз, сразу понимал **что это за игра, почему она устроена именно так,
> откуда взялись текущие компромиссы и куда проект движется**.
> Технический справочник по запуску и API — в `README.md`. Здесь — смысл, идеология и тонкости.

---

## 1. Что это такое (одним абзацем)

**Браузерная пошаговая PvP-игра на квадратной сетке**, выросшая из более крупной идеи
«2D-платформера с локациями, лобби, арсеналом и экипировкой». Сейчас существует только
её сердцевина — **боевой стенд**: пять соединённых дверями комнат (A1, A5, B1, E1, E5 из
плановой сетки 5×5) и полностью серверная боевая логика. Персонажей «из коробки» больше
нет: с Этапа 1 каждый боец появляется только когда игрок подключается через форму
настройки `game.html` → `php/join.php` (0 игроков = 0 персонажей, максимум 4 слота).
Стек сознательно примитивен: **PHP + Redis + чистый HTML/CSS/vanilla JS**. Никаких React,
Node.js, npm, сборщиков и сторонних движков — ни в проде, ни в прототипах (см. раздел «Табу»).

Игра синхронизирует несколько вкладок браузера (каждая = игрок) через **long polling**:
весь авторитет над состоянием боя имеет сервер; клиент — это «тупая графическая обёртка»,
которая получает снимок мира и отрисовывает его.

## 2. Как проект дошёл до жизни такой (история и идеология)

Проект начинался так (суть исходного замысла):

- У автора **уже были** меню, фронтенд, персонажи, лобби, арсенал и локации — но не было
  **движка боя и передвижения**. Задача ставилась ровно одна: сделать минимально
  жизнеспособный изолированный бой «в одном помещении», который можно скачать целиком
  на USBWebServer в папку `/test/` и открыть по `http://localhost/test/game.html`.
- Жёсткие требования автора, которые объясняют **почему код выглядит именно так**:
  1. **«Никакого React — ни строчки, ни файла, ни упоминания»** — автор не знает React и
     не сможет разбирасть проект, где база логики в JS. Фронтенд нужен «просто как
     обёртка для графики, а не для логики».
  2. **Вся логика и все расчёты — только на PHP.** Клиент не считает ничего: ни урон,
     ни путь, ни правила.
  3. **Обмен между игроками — через long polling, состояние — в Redis.** Без WebSocket,
     без Node, без сокетных библиотек.
  4. Код должен быть понятен **«слабому разработчику PHP/HTML/CSS»** — поэтому функции
     маленькие, комментарии на русском, никаких абстракций «на вырост».
- Отсюда характерные черты, которые новичок может принять за недоработки, а это — осознанные решения:
  - Персонаж = **цветной div-квадрат с ником и «словом-анимацией»** (IDLE/MOVE/ATTACK/…),
    а не спрайт: анимации сознательно сделаны как показ/скрытие текстового контейнера.
  - Раньше данные персонажей были **захардкожены в `data/initial_snapshot.json`** (четыре
    заготовленных бойцов) как временная подставка под аккаунт игрока. С Этапа 1 снимок
    изначально пуст (`{"players": []}`): карточка персонажа составляется вручную на форме
    настройки `game.html` и уходит в `php/join.php` — это имитация будущих данных аккаунта
    из БД (меню аккаунта уже существует, но с движком пока не связано). Характеристики
    объектов/ловушек/NPC — кодом в реестре `systems/objects.php::getObjectTemplates()`,
    их расстановка — секциями карт комнат (NPC/объектам владелец не нужен).
    Система экипировки намеренно не реализована, т.к. для тестового стенда она не требовалась.
  - Способности и пассивки прописаны кодом в реестрах `systems/abilities.php` / `systems/passives.php`
    / `systems/objects.php`, а не данными, — это точки расширения, куда автор планировал
    подключить настоящую систему предметов.

### Табу (не нарушать никогда)
- ❌ React / Vue / Angular / любой фреймворк — даже «минимальный, даже для демонстрации».
- ❌ Node.js, npm, yarn, сборщики (webpack/vite/esbuild).
- ❌ Логика игры на клиенте. JS на клиенту разрешён ровно в трёх ролях: polling, рендер, ввод.
- ❌ WebSocket / SSE вместо long polling (по исходному ТЗ; при миграции — только по решению автора).

> Примечание: живой клиент — `game.html` + `js/*.js` (модули config/state/utils/grid/path/animation/render/input/net/main) + `css/game.css`. Ранние relics
> песочничной сборки удалены из репозитория.

```

                       форма настройки персонажа (uid/ник, характеристики 1..10 + очки действий 1..3,
                       выбор ровно 3 способностей и 0..5 пассивок) и боевой экран после joinGame()
css/game.css       — вся визуальщина: клетки, квадраты персонажей, «анимации-слова», снаряды, форма настройки
js/                  — клиент, модули: config, state, utils, grid, path, animation, render, input, net, main
                     (в песочнице подключаются в game.html; long-poll цикл, отрисовка, клик-меню, движение)
diag.html          — диагностика окружения (PHP/Redis видимость)
data/initial_snapshot.json — ИЗНАЧАЛЬНЫЕ бойцы: с Этапа 1 изначально пуст (`{"players": []}`) —
                       персонажи «без владельца» в мире не существуют; состав боя присылает
                       php/join.php (карточка с формы). Формат сохранён как резервная схема снимка

data/A5.json         — карта комнаты-угла A5 (16×12), то же форматно
data/B1.json         — центральная комната B1 (16×12): 4 двери по углам (в A1/A5/E1/E5),
                       стена в столбце 7; в секциях objects/traps/npcs — стартовая расстановка
                       двух бочки, мины и турели (характеристики типа — код-реестр getObjectTemplates())
data/E1.json         — карта комнаты-угла E1 (16×12)
data/E5.json         — карта комнаты-угла E5 (16×12)
php/config.php       — только Redis-подключение + JSON-хелперы + лог (константы мира переехали в engine/rules.php)
php/engine/world_builder.php — ★ сборщик ИЗНАЧАЛЬНОГО состояния мира (код-реестры + карты + снимок)
php/engine/world_reset.php   — ★ перезапуск сессии: build + write (flushDB, version=1, метка seeded)
tools/reset_world.php        — CLI сброс мира (он же — init.php?reset=1)
php/init.php         — проверка готовности мира в Redis (идемпотентен) + явный ?reset=1, создание сессии боя;
                       отдаёт реестры abilities/passives для формы настройки game.html
php/join.php         — ★ HTTP-вход подключения игрока (Этап 1): POST JSON-карточка персонажа

php/action.php     — HTTP-вход для всех действий игроков (POST move/attack/ability): валидация → системы

php/battle.php     — ФАСАД обратной совместимости: старые имена функций → делегаты в engine/systems

php/engine/geometry.php — чистые функции координат/путей
php/engine/events.php   — событийная шина: hook/emit/emitReduce (канонический список событий в шапке)
php/engine/world.php    — единственный владелец Redis-хранилища (load/save/init/log/version)
php/engine/turn.php     — оркестратор тика хода (движение→смерть→снаряды→NPC→эффекты) и начала нового хода

php/systems/passives.php— ТОЛЬКО пассивки игроков как слушатели шины (REGENERATION, ARMORED, ARMOR_CRUSH,

php/systems/targeting.php— универсальный доступ к сущностям/целям (AoE бьёт игроков, NPC, объекты)
php/systems/abilities.php— определения способностей + 4 механизма применения (через combat/effects сервисы)
php/systems/objects.php — автономные объекты: NPC (зоны угрозы, LOS, ИИ-атака раз в ход, не стреляет по

php/systems/rooms.php   — мультикомнатный мир: ленивая загрузка карт data/<ID>.json в state['rooms'],

php/debug.php      — диагностика движка: PHP/Redis, загрузка модулей, реестры, состав мира в Redis,

                     tools/reset_world.php / init.php?reset=1

```

Поток данных: `init.php` наполняет Redis (после reset состав бойцов пуст) → игрок подключается
`join.php` (карточка с формы настройки → боец в мире) → клиент крутит `poll.php` (держит запрос до ~25 сек,
просьба к серверу «сообщить, когда version изменится») → клики клиента летят в `action.php` →
валидация и роутинг в `systems/*`; механики общаются между собой событиями шины (`engine/events.php`),
а с хранилищем — только через `engine/world.php`; любое изменение инкрементит версию в `world_save()` →
зависнувший `poll.php` мгновенно отдаёт новый snapshot всем.
⚠️ Явной блокировки/транзакций между параллельными запросами в коде нет — состояние читается
и пишется целиком (read-modify-write), «гонки» гасятся тем, что операции короткие, а проверка
занятости клетки учитывает END_POSITION движущихся игроков (мёртвые DEATH/DECAY/REMOVED клетку
не занимают). Это осознанный минимализм стенда.

Ключевые Redis-ключи (префикс `battle:`): `players`, `objects`, `traps`, `npcs`, `room`
(legacy-карта единой комнаты для отладочных путей), `room:<ID>` + `room:list` (карты реально
использованных комнат — в Redis не лежат все 25 помещений, только «оседлавшие» мир),
`turn_time`, `projectiles`, `version`, `log` + `world_move_now` (виртуальные часы движения,
отдельный ключ — обновляется каждый тик без инкремента версии) + `action_acks` (hash журнал
подтверждений применённых действий — идемпотентность повторных запросов из action.php).

## 4. Модель мира — главное, что надо понять

- **Сетка 16×12** (X — ширина, Y — высота) — она едина для ВСЕХ комнат: координаты разных
  комнат ПЕРЕКРЫВАЮТСЯ (клетка `5,5` живёт одновременно и в A1, и в B1). Отсюда главный
  инвариант мира — **изоляция по комнатам**: любая проверка позиции (цели, лучи, AoE, зоны
  угрозы, ловушки, занятость/проходимость клеток) обязана фильтровать сущности по `ROOM_ID`.
- **Мультикомнатный мир** (`php/systems/rooms.php`): состояние хранит словарь
  `state['rooms'] = {ID => карта}`; карты грузятся **лениво** из `data/<ID>.json` при первом
  обращении — добавление новой комнаты это новый JSON + запись в `exits` соседних, без правок
  кода. Расчётная архитектура — сетка 5×5 (A..E × 1..5, 25 помещений); сейчас в данных пять
  комнат: центральная **B1** и четыре угла **A1 / A5 / E1 / E5**.
- **Двери (exit)** — постоянные триггеры в карте: `exits["x,y"] = КУДА`,
  `exit_rooms["x,y"] = ОТКУДА` (обратная дверь), `exit_positions["x,y"]` — эталонная клетка
  появления у двери. Срабатывают по тому же принципу, что LAND_MINE: **достаточно наступить**
  на клетку (проверка в финале движения `movement_update()` → `rooms_check_exit_trigger`).
  Дверь не исчезает после срабатывания и доступна повторно любому игроку. Схема связей:
  A1 `0,0` ↔ B1, A5 `15,0` ↔ B1, E1 `0,11` ↔ B1, E5 `15,11` ↔ B1 (у B1 — все четыре угла).
- **Переход между комнатами** — `rooms_teleport()`: игрок «выписывается» из старой комнаты
  (движение обрывается), получает новый `ROOM_ID` и появляется у двери новой комнаты на
  **ближайшей свободной клетке** (защита от body-block: если клетка у двери занята другим
  бойцом — берётся следующая по удалённости; на саму дверь вставать нельзя — иначе первый же
  тик вернул бы повторный переход). Эмитится fact-событие шины `room.changed`.
- **Комната B1**: сплошная вертикальная стена в столбце 7 (кроме краёв) делит её на две
  половины; в ней же стартовые бочки, мина и турель. Поля `stairs` в картах пока пустуют —
  «этажи с лестницами» из концепта 2D-платформера законсервированы.
- **Legacy-режим**: `state['room']` — единая карта (её читают debug-эндпоинты и вызовы без
  room_id); при мультикомнатном бое это карта комнаты с сущностями (B1). poll без `?player=`
  отдаёт именно её.
- **Сущности** (поля намеренно в CAPS — стиль наследован из исходного ТЗ):
  - Игрок: UID (id аккаунта из карточки join.php), NICKNAME, CHAR_ID ('CUSTOM' у подключённых),
    ALLY (не более одного союзника или NONE; join.php ставит NONE — FFA до лобби), ROOM_ID (текущая
    комната), SPAWN_ROOM (личная комната возрождения),
    START/CUR/END_POSITION_XY, STATUS, TURN, HITPOINTS, RESISTANCE, SHIELD, ATTACK,
    ACTIONS, RANGE, ABILITIES, PASSIVES, NEGATIVES, LIFE, COLOR.
  - Разрушаемый объект (бочки): OBJECT_ID, IMAGE, ROOM_ID, POSITION_XY, STATUS(INTACT/DESTROYED), HITPOINTS.
  - Ловушка (мина): TRAP_ID, ALLY (NONE = бьёт всех; иначе щадит владельца и его союзника),
    ROOM_ID, POSITION_XY, RANGE, EFFECT (список негативов), DAMAGE, HITPOINTS.
  - Стационарный NPC (турель): NPC_ID, ALLY, CUR_TARGET, ROOM_ID, ATTACK, ACTIONS, RANGE, HITPOINTS.

## 5. Бой: правила и тонкости (то, что легко неверно прочитать в коде)

### Ход и очки действий
- Мир «тикает» каждые **TURN_DURATION = 5 секунд**: всем игрокам ACTIONS восстанавливается
  до MAX_ACTIONS (накопить очки нельзя; у подключённых через join.php MAX_ACTIONS = значение
  из карточки, 1..3), регенерируется SHIELD (+1 за ход до максимума),
  тикают NEGATIVES, срабатывает REGENERATION, действует DoT (DOT[N]).
  ⚠️ В исходном ТЗ ход был 10 секунд — сокращено для отзывчивости теста.
- Очерёдности ходов **нет**: все играют одновременно в реальном времени, ограничены только
  очками. Любое действие стоит ровно 1 очко. Кулдаунов нет.

### Передвижение
- Только по прямой (одна ось), максимум **5 клеток** (SWIFT +1, SLOWED −2, минимум 1).
  Все проверки пути (стены, препятствия, занятость) идут **по карте комнаты игрока**.
- Движение **плавное и предсказанное сервером**: сервер считает длительность
  (MOVE_SPEED = 3 клетки/сек), фиксирует MOVE_START_TIME/MOVE_END_TIME, а клиент просто
  интерполирует позицию между START и END до наступления END_TIME. Авторитет — время сервера.
- Во время MOVING нельзя атаковать/кастовать; **получение урона прерывает движение**
  (игрок останавливается на достигнутой клетке) — это осознанное правило из ТЗ.
- Путь проверяется клетка-за-клеткой: стены, другие игроки (включая тех, кто *летит* в эту
  клетку — race-condition решён проверкой END_POSITION других MOVING-игроков; мёртвые
  DEATH/DECAY/REMOVED клетку не занимают), разрушенные объекты и живые NPC (турель —
  непроходимое препятствие, пока жива). Кто первый занял клетку — того и место.
- **Ловушки срабатывают на всём пути**, не только в конечной точке: игрок встаёт на клетку
  мины, получает DAMAGE + EFFECT, и движение обрывается.
- **Зоны угрозы NPC**: турель «держит» прямые линии своей дальности; если траектория движения
  пересекает зону угрозы враждебного NPC — NPC стреляет по движущейся цели, вплоть до остановки
  (и смерти) игрока посреди пути. Механика «walk into fire» — одна из самых гордых находок стенда.
  При выстреле NPC получает STATUS = 'ATTACK' (анимация как у игроков), который сбрасывается в
  IDLE функцией `objects_update_npc_statuses()` (движок-тик `turn_tick`, каждый poll) через 1 секунду.

### Атака и урон
- Базовая атака — «выстрел по прямой» в пределах RANGE: луч идёт клетка-за-клеткой;
  **без PUNCTURE луч останавливается на первом враге/препятствии**, с PUNCTURE (пассивка)
  пробивает сквозь цели дальше. Стены, бочки и живые NPC блокируют всегда.
- Формула (единая цепочка `combat_apply_damage`, systems/combat.php): база от ATTACK,
  сопротивление цели режет урон (каждое очко RESISTANCE = −10%), итог округляется
  **в большую сторону** (`ceil`, дробей в уроне нет), floor-гарантия: **минимум 1 unit всегда
  проходит**. Если у атакующего **ARMOR_CRUSH** (и при этом нет ARMORED) — сопротивление цели
  игнорируется полностью.
- Щит гасит удар первым, затем HP. **ARMORED** у цели снижает входящий урон вдвое, но только
  от атакующих с ARMOR_CRUSH (переработанная механика; на обычные атаки и NPC не действует).
  THORNS возвращает 1 урона атакующему при поражении цели, SPLASH задевает соседей цели.
  Урон NPC (турель/мина) идёт без сопротивления цели — одинаковый ко всем. Прерывание движения
  происходит только при реально нанесённом уроне (щит поглотил — идём дальше).

### Способности
- Прописаны в `systems/abilities.php`; у бойца хранятся в формате `"НАЗВАНИЕ[N]"`, где **N — дальность
  применения** (не стоимость!; range проставляет join.php из реестра — клиенту он недоступен для подделки).
  Способность также тратит 1 очко и применяется по прямой,
  как движение/атака.
- Четыре механизма (`projectile`): `none` — мгновенный ближий эффект (BACKSTAB, SHIELD BASH),
  `beam` — луч до первой цели (ICE SHARD, POISON BLADE), `line` — волна по линии сквозь
  промежуточных (FIRE WAVE), `area` — взрыв с радиусом aoe вокруг точки (гранаты, NOVA, BLIZZARD).
  Плюс self_buff (FORTIFY: +3 щита) и ally_buff (WAR CRY: +2 ATTACK союзникам в зоне).
- Визуализация — контейнеры-снаряды с фазами cast/hit, живут в Redis-ключе `projectiles`,
  клиент их доигрывает и забывает.

### Негативы
Формат `ЭФФЕКТ[ходов]`: PARALYZED (полный блок), STUNNED (блок; активируется немедленно при наложении, в т.ч. от ловушки в середине движения), SLOWED (−2 движения),
DOT (универсальный постепенный урон по 1 за ход, заменил BLEED/POISONED), BLINDED. Снимаются счётчиком ходов на tick'е.

### Двери и переходы между комнатами
- Наступить на клетку `exits` — тот же принцип, что «встать на мину»: в финале движения
  `movement_update()` вызывает `rooms_check_exit_trigger()` → `rooms_teleport(reason='exit')`.
- Телепорт **мгновенный** (не путь по сетке): сервер выдаёт «виртуальный» финал MOVING с
  `MOVE_END_TIME` в прошлом, и ближайший тик штатно доводит статус до IDLE (или
  восстанавливает STUNNED из активных NEGATIVES) — прямая установка IDLE ломала клиентскую
  подсветку зон и вызывала «рывок к exit».
- Точка появления: приоритет — **обратная дверь** (`exit_rooms["x,y"] == ОТКУДА`), иначе любая
  exit-клетка комнаты, иначе центр карты (страховка). Кандидаты сортируются «кольцами» от
  двери, внутри кольца — с приоритетом направления ВГЛУБЬ комнаты; все двери комнаты исключены
  из кандидатов (встать на дверь нельзя — получил бы повторный переход на первом же тике).
- Если ближайшая свободная клетка занята другим бойцом — берётся следующая по удалённости
  (body-block двери не возможен). Не найдено ни одной клетки — переход отклонён с записью в лог.
- Клиент при смене `room_id` в poll-ответе перестраивает сетку (`rebuildGrid`), сбрасывает
  локальные анимации движения и удаляет «осиротевшие» div'ы прежней комнаты
  (`purgeOutOfViewRoomEntities`).

### Подключение игрока (Этап 1: join.php)
- Персонажей «без владельца» в мире нет: боец появляется только после успешного входа.
  **0 подключившихся = 0 персонажей, N игроков = N бойцов** (до 4). NPC/объекты/ловушки
  расставляются из карт комнат как прежде — владелец им не нужен.
- Клиент собирает карточку на форме `game.html` и шлёт POST в `php/join.php`; сервер
  **не доверяет клиенту**: заново валидирует uid/nickname/статы против правил формы,
  сверяет способности и пассивки с реестрами движка (`getAbilityDefinitions()` /
  `getPassiveDefinitions()`), range способностей берётся из реестра, а не из запроса.
- Слот спавна определяется uid: 1..4 → комнаты A1/A5/E1/E5 (личная spawn_cell карты,
  иначе ближайшая свободная клетка). ALLY = NONE для всех — союзов пока нет, их
  определит лобби; состав боя при этом FFA.
- Запись бойца — CAS по версии мира (`world_save_cas`): параллельный тик `poll.php`
  или чужое подключение не затираются; при гонке — rebase и повтор (до 3 попыток).
- Повторный вход того же uid идемпотентен (ответ `rejoin:true` — перезагрузка страницы
  не создаёт второго персонажа); занятый ник другого игрока — HTTP 409.
- Ограничение статичной сессии (известная незакрытая проблема, решена поверхностно):
  пятый игрок получает HTTP 409 «все спавн-места заняты», пока сессия не перезапущена
  (`init.php?reset=1`). Фундамент (эндпоинт + карточка + CAS) готов к мультисессии с лобби.

### Смерть, распад и возрождение
- Цепочка статусов: `DEATH` (1 сек) → `DECAY` (1 сек) → если `LIFE > 0`: −1 жизнь, полный
  reset HP/щита и **респаун через `rooms_teleport(..., reason='respawn')` в личную
  `SPAWN_ROOM`**: боец возвращается на свою `START_POSITION_XY` (личная спавн-клетка), а если
  она занята или является дверью — на ближайшую свободную клетку рядом (с тем же правилом
  «не вставать на дверь»); статус `IDLE`. Если жизни кончились — `REMOVED` (игрок исключается
  из действий/целей; позиция при этом не перестирается).
- Страховка legacy: если телепорт в `SPAWN_ROOM` невозможен (нет карты/свободной клетки) —
  возврат на `START_POSITION_XY` внутри текущей комнаты; если `SPAWN_ROOM` не задана —
  респаун там, где боец и умер.
- Визуально: DEATH и DECAY — простые 1-секундные CSS-анимации содержимого блока (без
  opacity/scale-эффектов, задел под будущие спрайт-анимации); div остаётся на клетке всё
  время обеих стадий и удаляется из DOM только когда сервер выставил `REMOVED` (жизни
  кончились) или когда игрок возродился в IDLE — так death+decay гарантированно
  проигрываются целиком, включая направление TURN.
- ALLY связывает ровно двух игроков (в исторической сборке — PLAYER1↔PLAYER2; союзов в текущем
  составе нет); союзники не могут стрелять друг в друга,
  нейтральные (ALLY=NONE) — легитимные мишени. Подключённые через join.php бойцы всегда ALLY=NONE (FFA до лобби).
  Победа пока = «остался не более одного живого»
  (`engine_check_victory`: alive ≤ 1 без командной привязки), матч-логики вне стенда нет.

## 6. Состав боя (Этап 1: игрок собирает карточку сам)

С Этапа 1 заготовленных персонажей в мире нет — состав боя динамический: каждый
подключившийся игрок приносит собственную карточку через форму `game.html` → `php/join.php`:

| Поле карточки | Правила (валидируются и на клиенте, и сервером) |
|---|---|
| uid | числовый id аккаунта «из БД» (ручной ввод — имитация); 1..4 = слот спавна → A1/A5/E1/E5 |
| nickname | ник «из БД», 1..24 символа (буквы/цифры/_/-/пробел); уникален среди подключённых |
| характеристики | HITPOINTS, SHIELD, ATTACK, RESISTANCE, RANGE — целые 1..10 (RESISTANCE в форме 1..9); ACTIONS (очки действий) — 1..3; MAX_* = стартовые значения |
| abilities | ровно 3 из реестра `systems/abilities.php` (мульти-селектор; range берётся из реестра) |
| passives | от 0 до 5 из реестра `systems/passives.php` (чекбоксы) |

Правило мира: **N подключившихся игроков = N персонажей, 0 игроков = 0 персонажей** —
персонажей «без владельца» не существует. NPC/мины/бочки/препятствия расставляются из карт
комнат как прежде: у них владельца нет и не нужно. Пятый игрок не помещается (HTTP 409) —
поверхностное решение ограничения одной статичной сессии до появления лобби.

Стартовые клетки бойцов — spawn_cells комнат A1/A5/E1/E5, совпадающие с `exit_positions`
дверей B1: боец стартует «в углу» своей комнаты рядом с дверью в центральный зал (там бочки,
мина и турель) — стенд сразу проверяет и переходы, и респаун в другую комнату.

Историческая справка: раньше четвёрку фиксированных классов (NAPALM UNIT / FROST KNIGHT /
SHADOW ROGUE / IRON GUARD, покрывавших все четыре механизма способностей none/beam/line/area)
задавал `data/initial_snapshot.json`. Снимок теперь пуст, но эти комбинации статов/способностей
доступны для ручного воспроизведения на форме — задуманное покрытие всех механизмов сохраняется.

## 7. Известные «скелеты в шкафу» (не баги — консервы)

1. **Этажи и лестницы (A1/C1 из концепта)** — концепт 2D-платформера заморожен до лучших
   времён: в картах комнат поле `stairs` присутствует во всех JSON, но пустое; вертикальных
   переходов код не реализует (горизонтальные — работают).
2. **Расширение мира за 5 комнат** — сетка рассчитана на 25 помещений (A..E × 1..5), но
   созданы и соединены только центральная B1 и четыре угла. Добавление комнаты — новый
   `data/<ID>.json` + запись в `exits` соседних, без правок кода (см. раздел 4).
3. **Интерактивные объекты** (KEY_TERMINAL и т.п.) — описаны типами в ТЗ, в data только бочки.
4. **Лобби/арсенал/экипировка** — существуют только в голове автора и исходном концепте.
   С Этапа 1 карточка персонажа собирается вручную на форме `game.html` (uid/nickname —
   ручной ввод, имитация данных аккаунта из БД) и уходит в `php/join.php`; меню аккаунта
   уже есть, но с движком не связано. Одна статичная сессия без подбора: максимум 4 слота,
   пятый подключившийся получает HTTP 409 — известное поверхностное решение до лобби;
   фундамент (эндпоинт + контракт карточки + CAS-запись) заготовлен под мультисессию.
5. **TURN (направление)** — обновляется сервером при горизонтальных действиях и визуально зеркалит спрайт (`turn-left`), но на геймплей (спина/фланг) пока не влияет.

## 9. Мини-гайд «как править, не сломав философию»

- **Прежде чем что-то чинить — сверьтесь с разделами 2 и 7**: то, что выглядит костылём,
  часто является осознанной консервой или требованием автора (стек-табу важнее «best practices»).
- Новое действие/правило → функция в нужной системе `systems/*` (+ вход POST-параметром в
  `action.php`), никогда не считайте правила на клиенте. Фасад `battle.php` — только legacy-алиасы,
  новый код туда не писать.
- Новая способность → запись в `getAbilityDefinitions()` (один из 4 механизмов) — она
  автоматически появится в селекторе формы `game.html` (реестры отдаёт init.php) и станет
  доступной через `join.php`; формат строки бойца в мире — `ИМЯ[range]`, range всегда
  берётся из реестра. Новый механизм — отдельный `case` в `applyAbility`
  (`systems/abilities.php`).
- Новая пассивка → `getPassiveDefinitions()` (`systems/passives.php`) + слушатель шины:
  `turn.start`, `damage.query_mitigate`, `damage.dealt`, `attack.resolved`,
  `movement.query_distance` (регистрация — в `passives_register_hooks()`); чекбокс на форме
  появится сам (список тоже из реестра через init.php).
- Изменение карточки подключения / правил входа → `php/join.php` (контракт) + форма
  `game.html`/`js/main.js` (клиентская половина тех же правил); серверная валидация
  обязательна — клиенту не доверяем.
- Любая мутация состояния обязана увеличить `REDIS_VERSION` (это делает `world_save()`) —
  иначе poll не проснётся и клиенты «зависнут на старом мире».
- После правок — перезапуск не нужен: достаточно нового init.php (он пересобирает Redis с нуля;
  состав бойцов после reset пуст — подключайте игроков через форму).
- Тест: несколько вкладок game.html, разные uid (1..4 — слоты спавна); debug.php покажет сырое состояние,
  diag.html — жив ли Redis. CLI-харнесс `tests/harness_engine.php` (in-memory фейк Redis)
  позволяет прогнать bootstrap/инициализацию движка без запущенного redis-server.
