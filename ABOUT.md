# ABOUT THE GAME — полный контекст проекта для разработчика / LLM

> Этот файл — «карта сознания» проекта. Его цель: любой новый читатель (человек или LLM),
> прочитав его один раз, сразу понимал **что это за игра, почему она устроена именно так,
> откуда взялись текущие компромиссы и куда проект движется**.
> Технический справочник по запуску и API — в `README.md`. Здесь — смысл, идеология и тонкости.

---

## 1. Что это такое (одним абзацем)

**Браузерная пошаговая PvP-игра на квадратной сетке**, выросшая из более крупной идеи
«2D-платформера с локациями, лобби, арсеналом и экипировкой». Сейчас существует только
её сердцевина — **изолированный боевой стенд**: одна комната `B1`, четыре тестовых персонажа,
полностью серверная боевая логика. Стек сознательно примитивен: **PHP + Redis + чистый
HTML/CSS/vanilla JS**. Никаких React, Node.js, npm, сборщиков и сторонних движков —
ни в проде, ни в прототипах (см. раздел «Табу»).

Игра синхронизирует несколько вкладок браузера (каждая = игрок) через **long polling**:
весь авторитет над состоянием боя имеет сервер; клиент — это «тупая графическая обёртка»,
которая получает снимок мира и отрисовывает его.

## 2. Как проект дошёл до жизни такой (история и идеология)

Проект начинался так (суть исходного замысла):

- У автора **уже были** меню, фронтенд, персонажи, лобби, арсенал и локации — но не было
  **движка боя и передвижения**. Задача ставилась ровно одна: сделать минимально
  жизнеспособный изолированный бой «в одном помещении», который можно скачать целиком
  на USBWebServer в папку `/test/` и открыть по `http://localhost/test/game.html`.
- Жёсткие требования автора, которые объясняют **почему код выглядит именно так**:
  1. **«Никакого React — ни строчки, ни файла, ни упоминания»** — автор не знает React и
     не сможет разбирасть проект, где база логики в JS. Фронтенд нужен «просто как
     обёртка для графики, а не для логики».
  2. **Вся логика и все расчёты — только на PHP.** Клиент не считает ничего: ни урон,
     ни путь, ни правила.
  3. **Обмен между игроками — через long polling, состояние — в Redis.** Без WebSocket,
     без Node, без сокетных библиотек.
  4. Код должен быть понятен **«слабому разработчику PHP/HTML/CSS»** — поэтому функции
     маленькие, комментарии на русском, никаких абстракций «на вырост».
- Отсюда характерные черты, которые новичок может принять за недоработки, а это — осознанные решения:
  - Персонаж = **цветной div-квадрат с ником и «словом-анимацией»** (IDLE/MOVE/ATTACK/…),
    а не спрайт: анимации сознательно сделаны как показ/скрытие текстового контейнера.
  - Данные персонажей и предметов **захардкожены в `data/battledata.json`** — система
    экипировки намеренно не реализована, т.к. для тестового стенда она не требовалась.
  - Способности и пассивки прописаны кодом в реестрах `systems/abilities.php` / `systems/passives.php`
    / `systems/objects.php`, а не данными, — это точки расширения, куда автор планировал
    подключить настоящую систему предметов.

### Табу (не нарушать никогда)
- ❌ React / Vue / Angular / любой фреймворк — даже «минимальный, даже для демонстрации».
- ❌ Node.js, npm, yarn, сборщики (webpack/vite/esbuild).
- ❌ Логика игры на клиенте. JS на клиенту разрешён ровно в трёх ролях: polling, рендер, ввод.
- ❌ WebSocket / SSE вместо long polling (по исходному ТЗ; при миграции — только по решению автора).

> Примечание: живой клиент — `game.html` + `js/game.js` + `css/game.css`. Ранние relics
> песочничной сборки удалены из репозитория.

## 3. Карта файлов и кто за что отвечает

```
game.html          — страница боя (единственная живая точка входа клиента)
css/game.css       — вся визуальщина: клетки, квадраты персонажей, «анимации-слова», снаряды
js/game.js         — клиент: long-poll цикл, отрисовка state'а, клик-меню действий, плавное движение
diag.html          — диагностика окружения (PHP/Redis видимость)
data/battledata.json — стартовые игроки/объекты/ловушки/NPC (временный источник данных боя)
data/B1.json       — маска комнаты 16×12 (0 — проход, 1 — стена) + выходы/лестницы
php/config.php     — только Redis-подключение + JSON-хелперы + лог (константы мира переехали в engine/rules.php)
php/init.php       — загрузка battledata.json/B1.json в Redis (world_init), создание сессии боя
php/action.php     — HTTP-вход для всех действий игроков (POST move/attack/ability): валидация → системы
php/poll.php       — long polling + серверные часы: turn_tick на каждом запросе, отдаёт полный snapshot
php/battle.php     — ФАСАД обратной совместимости: старые имена функций → делегаты в engine/systems
php/engine/rules.php    — единый источник констант мира + правила для клиента (TURN-формула, payload `rules`)
php/engine/geometry.php — чистые функции координат/путей
php/engine/events.php   — событийная шина: hook/emit/emitReduce (канонический список событий в шапке)
php/engine/world.php    — единственный владелец Redis-хранилища (load/save/init/log/version)
php/engine/turn.php     — оркестратор тика хода (движение→смерть→снаряды→NPC→эффекты) и начала нового хода
php/engine/bootstrap.php— точка сборки: подключение систем + регистрация слушателей в фиксированном порядке
php/systems/effects.php — реестр статус-эффектов: длительность [N] ходов реально тикает и снимается
php/systems/combat.php  — единая цепочка урона (сопротивление/пробитие → щит → HP → смерть) + атаки
php/systems/movement.php— движение: предсказание на копии vs применение, блокировки/дальность через шину
php/systems/passives.php— ТОЛЬКО пассивки игроков как слушатели шины (REGENERATION, ARMORED, ARMOR_CRUSH,
                          SPLASH, THORNS, SWIFT/SLOWED, PUNCTURE)
php/systems/targeting.php— универсальный доступ к сущностям/целям (AoE бьёт игроков, NPC, объекты)
php/systems/abilities.php— определения способностей + 4 механизма применения (через combat/effects сервисы)
php/systems/objects.php — автономные объекты: NPC (зоны угрозы, LOS, ИИ-атака раз в ход, не стреляет по
                          мёртвым) и ловушки; задел под объекты, создаваемые способностями
php/debug.php      — диагностика движка: PHP/Redis, загрузка модулей, реестры, тест цикла (⚠️ flushDB)
```

Поток данных: `init.php` наполняет Redis → клиент крутит `poll.php` (держит запрос до ~25 сек,
просьба к серверу «сообщить, когда version изменится») → клики клиента летят в `action.php` →
валидация и роутинг в `systems/*`; механики общаются между собой событиями шины (`engine/events.php`),
а с хранилищем — только через `engine/world.php`; любое изменение инкрементит версию в `world_save()` →
зависнувший `poll.php` мгновенно отдаёт новый snapshot всем.
⚠️ Явной блокировки/транзакций между параллельными запросами в коде нет — состояние читается
и пишется целиком (read-modify-write), «гонки» гасятся тем, что операции короткие, а проверка
занятости клетки учитывает END_POSITION движущихся игроков (мёртвые DEATH/DECAY/REMOVED клетку
не занимают). Это осознанный минимализм стенда.

Ключевые Redis-ключи (префикс `battle:`): `players`, `objects`, `traps`, `npcs`, `room`,
`turn_time`, `projectiles`, `version`, `log` + `world_move_now` (виртуальные часы движения,
отдельный ключ — обновляется каждый тик без инкремента версии).

## 4. Модель мира — главное, что надо понять

- **Сетка 16×12** (X — ширина, Y — высота). Всё решается «по клеткам»: в клетке живёт
  игрок / объект / стена / выход. Координаты хранятся строкой `"x,y"` (`CUR_POSITION_XY` и т.п.).
- **Комната B1**: сплошная вертикальная стена в столбце 7 (кроме краёв) делит её на две половины;
  верхняя брешь `7,0` ведёт в комнату A1, нижняя `7,11` — в C1. **Переходы между комнатами —
  заглушка**: карта уже описывает exits/stairs, но сервер переноса между комнатами не делает.
  A1/C1 — изначальная идея «трёх этажей с лестницами» (2D-платформер), пока законсервирована.
- **Сущности** (поля намеренно в CAPS — стиль наследован из исходного ТЗ):
  - Игрок: NICKNAME, CHAR_ID, ALLY (не более одного союзника или NONE), ROOM_ID,
    START/CUR/END_POSITION_XY, STATUS, TURN, HITPOINTS, RESISTANCE, SHIELD, ATTACK,
    ACTIONS, RANGE, ABILITIES, PASSIVES, NEGATIVES, LIFE, SPAWN_ROOM, COLOR.
  - Разрушаемый объект (бочки): OBJECT_ID, IMAGE, POSITION_XY, STATUS(INTACT/DESTROYED), HITPOINTS.
  - Ловушка (мина): TRAP_ID, ALLY (NONE = бьёт всех; иначе щадит владельца и его союзника),
    RANGE, EFFECT (список негативов), DAMAGE, HITPOINTS.
  - Стационарный NPC (турель): NPC_ID, ALLY, CUR_TARGET, ATTACK, ACTIONS, RANGE, HITPOINTS.

## 5. Бой: правила и тонкости (то, что легко неверно прочитать в коде)

### Ход и очки действий
- Мир «тикает» каждые **TURN_DURATION = 5 секунд**: всем игрокам ACTIONS восстанавливается
  до MAX_ACTIONS (накопить очки нельзя), регенерируется SHIELD (+1 за ход до максимума),
  тикают NEGATIVES, срабатывает REGENERATION, действуют DoT (BLEED/POISONED).
  ⚠️ В исходном ТЗ ход был 10 секунд — сокращено для отзывчивости теста.
- Очерёдности ходов **нет**: все играют одновременно в реальном времени, ограничены только
  очками. Любое действие стоит ровно 1 очко. Кулдаунов нет.

### Передвижение
- Только по прямой (одна ось), максимум **5 клеток** (SWIFT +N, SLOWED −2, минимум 1).
- Движение **плавное и предсказанное сервером**: сервер считает длительность
  (MOVE_SPEED = 3 клетки/сек), фиксирует MOVE_START_TIME/MOVE_END_TIME, а клиент просто
  интерполирует позицию между START и END до наступления END_TIME. Авторитет — время сервера.
- Во время MOVING нельзя атаковать/кастовать; **получение урона прерывает движение**
  (игрок останавливается на достигнутой клетке) — это осознанное правило из ТЗ.
- Путь проверяется клетка-за-клеткой: стены, другие игроки (включая тех, кто *летит* в эту
  клетку — race-condition решён проверкой END_POSITION других MOVING-игроков; мёртвые
  DEATH/DECAY/REMOVED клетку не занимают), разрушенные объекты и живые NPC (турель —
  непроходимое препятствие, пока жива). Кто первый занял клетку — того и место.
- **Ловушки срабатывают на всём пути**, не только в конечной точке: игрок встаёт на клетку
  мины, получает DAMAGE + EFFECT, и движение обрывается.
- **Зоны угрозы NPC**: турель «держит» прямые линии своей дальности; если траектория движения
  пересекает зону угрозы враждебного NPC — NPC стреляет по движущейся цели, вплоть до остановки
  (и смерти) игрока посреди пути. Механика «walk into fire» — одна из самых гордых находок стенда.
  При выстреле NPC получает STATUS = 'ATTACK' (анимация как у игроков), который сбрасывается в
  IDLE функцией `objects_update_npc_statuses()` (движок-тик `turn_tick`, каждый poll) через 1 секунду.

### Атака и урон
- Базовая атака — «выстрел по прямой» в пределах RANGE: луч идёт клетка-за-клеткой;
  **без PUNCTURE луч останавливается на первом враге/препятствии**, с PUNCTURE (PLAYER1/2)
  пробивает сквозь цели дальше. Стены, бочки и живые NPC блокируют всегда.
- Формула (единая цепочка `combat_apply_damage`, systems/combat.php): база от ATTACK,
  сопротивление цели режет урон (каждое очко RESISTANCE = −10%), итог округляется
  **в большую сторону** (`ceil`, дробей в уроне нет), floor-гарантия: **минимум 1 unit всегда
  проходит**. Если у атакующего **ARMOR_CRUSH** (и при этом нет ARMORED) — сопротивление цели
  игнорируется полностью.
- Щит гасит удар первым, затем HP. **ARMORED** у цели снижает входящий урон вдвое, но только
  от атакующих с ARMOR_CRUSH (переработанная механика; на обычные атаки и NPC не действует).
  THORNS возвращает 1 урона атакующему при поражении цели, SPLASH задевает соседей цели.
  Урон NPC (турель/мина) идёт без сопротивления цели — одинаковый ко всем. Прерывание движения
  происходит только при реально нанесённом уроне (щит поглотил — идём дальше).

### Способности
- Прописаны в `systems/abilities.php`; в `battledata.json` формат `"НАЗВАНИЕ[N]"`, где **N — дальность
  применения** (не стоимость!). Способность также тратит 1 очко и применяется по прямой,
  как движение/атака.
- Четыре механизма (`projectile`): `none` — мгновенный ближий эффект (BACKSTAB, SHIELD BASH),
  `beam` — луч до первой цели (ICE SHARD, POISON BLADE), `line` — волна по линии сквозь
  промежуточных (FIRE WAVE), `area` — взрыв с радиусом aoe вокруг точки (гранаты, NOVA, BLIZZARD).
  Плюс self_buff (FORTIFY: +3 щита) и ally_buff (WAR CRY: +2 ATTACK союзникам в зоне).
- Визуализация — контейнеры-снаряды с фазами cast/hit, живут в Redis-ключе `projectiles`,
  клиент их доигрывает и забывает.

### Негативы
Формат `ЭФФЕКТ[ходов]`: FROZEN (полный блок), STUNNED (блок; активируется немедленно при наложении, в т.ч. от ловушки в середине движения), SLOWED (−2 движения),
BLEED/POISONED (DoT по 1 за ход), BLINDED. Снимаются счётчиком ходов на tick'е.

### Смерть, распад и возрождение
- Цепочка статусов: `DEATH` (1 сек) → `DECAY` (1 сек) → если `LIFE > 0`: −1 жизнь, полный
  reset HP/щита на **стартовую позицию** (`CUR_POSITION_XY = START_POSITION_XY`, без поиска
  свободной клетки рядом), статус `IDLE`; если жизни кончились — статус `REMOVED` (игрок
  исключается из действий/целей; позиция при этом не перестирается).
- Визуально: DEATH и DECAY — простые 1-секундные CSS-анимации содержимого блока (без
  opacity/scale-эффектов, задел под будущие спрайт-анимации); div остаётся на клетке всё
  время обеих стадий и удаляется из DOM только когда сервер выставил `REMOVED` (жизни
  кончились) или когда игрок возродился в IDLE — так death+decay гарантированно
  проигрываются целиком, включая направление TURN.
- ⚠️ Тонкость-заглушка: respawn переносит в `SPAWN_ROOM` (= 'SPAWN'), но **комнаты SPAWN не
  существует** — фактически игрок «воскресает» на старой позиции той же B1. Механика рабочая,
  но до полноценной комнаты спавна недотянута.
- ALLY связывает ровно двух игроков (PLAYER1↔PLAYER2); союзники не могут стрелять друг в друга,
  нейтральные (ALLY=NONE) — легитимные мишени. Победа пока = «остался не более одного живого»
  (`engine_check_victory`: alive ≤ 1 без командной привязки), матч-логики вне стенда нет.

## 6. Персонажи стенда (балансная идея)

| Игрок | Класс | Роль | Ключевое |
|---|---|---|---|
| PLAYER1 | NAPALM UNIT | гранатомётчик | AoE-урон огнём, BLEED; PUNCTURE |
| PLAYER2 | FROST KNIGHT | контроль | заморозка, AoE-лёд; ARMORED+SPLASH+PUNCTURE+ARMOR_CRUSH (ARMORED глушит собственный ARMOR_CRUSH), 3 AP |
| PLAYER3 | SHADOW ROGUE | ассасин | 7 ATK, BACKSTAB[1] (6 урона вблизи); SPLASH+ARMOR_CRUSH (пробивает сопротивление и ARMORED целей); без щита |
| PLAYER4 | IRON GUARD | танк-саппорт | 8 SHIELD, 7 RES; бафы FORTIFY/WAR CRY; всего 1 AP |

Четыре класса покрывают четыре механизма способностей (none/beam/line/area) — сделано специально,
чтобы весь код `systems/abilities.php` был виден вживую при тесте.

## 7. Известные «скелеты в шкафу» (не баги — консервы)

1. **Межкомнатные переходы** — заглушка (данные в B1.json есть, кода переноса нет).
2. **A1/C1 (этажи/лестницы)** — концепт 2D-платформера заморожен до лучших времён.
3. **LIFE/respawn** — логика DEATH→DECAY→возрождение написана, но «комнаты спавна» нет:
   respawn происходит на стартовой позиции той же B1.
4. **Интерактивные объекты** (KEY_TERMINAL и т.п.) — описаны типами в ТЗ, в data только бочки.
5. **Лобби/арсенал/экипировка** — существуют только в голове автора и исходном концепте;
   battledata.json — временная подставка под будущую систему предметов.
6. **TURN (направление)** — обновляется сервером при горизонтальных действиях и визуально зеркалит спрайт (`turn-left`), но на геймплей (спина/фланг) пока не влияет.

## 8. Куда проект растёт (маршрут, вытекающий из концепта)

1. Настоящая система экипировки: предметы в БД → генерация battledata → пассивки как данные, а не код.
2. Комната спавна + возрождение (LIFE), матч-цикл, счётчики побед.
3. Многокомнатность: перенос игроков между B1/A1/C1, «этажи с лестницами» из концепта.
4. Интерактивные объекты (терминалы, двери), режимы PvE против NPC-волн.
5. Перенос боевого ядра из тестовой комнаты в реальную игру: лобби → выбор персонажа/арсенала → бой.
6. Возможно — спрайты вместо «квадратов со словами», но только когда механика будет стабильна.

## 9. Мини-гайд «как править, не сломав философию»

- **Прежде чем что-то чинить — сверьтесь с разделами 2 и 7**: то, что выглядит костылём,
  часто является осознанной консервой или требованием автора (стек-табу важнее «best practices»).
- Новое действие/правило → функция в нужной системе `systems/*` (+ вход POST-параметром в
  `action.php`), никогда не считайте правила на клиенте. Фасад `battle.php` — только legacy-алиасы,
  новый код туда не писать.
- Новая способность → запись в `getAbilityDefinitions()` (один из 4 механизмов) + строка в
  `battledata.json` вида `ИМЯ[range]`. Новый механизм — отдельный `case` в `applyAbility`
  (`systems/abilities.php`).
- Новая пассивка → `getPassiveDefinitions()` (`systems/passives.php`) + слушатель шины:
  `turn.start`, `damage.query_mitigate`, `damage.dealt`, `attack.resolved`,
  `movement.query_distance` (регистрация — в `passives_register_hooks()`).
- Любая мутация состояния обязана увеличить `REDIS_VERSION` (это делает `world_save()`) —
  иначе poll не проснётся и клиенты «зависнут на старом мире».
- После правок — перезапуск не нужен: достаточно нового init.php (он пересобирает Redis с нуля).
- Тест: несколько вкладок game.html, разные PLAYER*; debug.php покажет сырое состояние,
  diag.html — жив ли Redis. CLI-харнесс `tests/harness_engine.php` (in-memory фейк Redis)
  позволяет прогнать bootstrap/инициализацию движка без запущенного redis-server.
