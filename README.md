# BATTLE SYSTEM - Browser Game Engine

Браузерная пошаговая боевая система (PvP на сетке) для браузерной игры. Бэкенд — чистый PHP + Redis (состояние боя хранится в Redis, синхронизация клиентов через long polling). Фронтенд — HTML/CSS/JS без фреймворков (React/Node.js не используются и не требуются).

> 📖 **Новичкам и LLM-ассистентам**: перед работой с кодом прочитайте [`ABOUT.md`](ABOUT.md) — там описаны смысл проекта, его идеология (почему стек именно такой и что запрещено менять), история возникновения, тонкости механик и список осознанных «заглушек», которые не следует принимать за баги.

## Быстрый старт

### Требования
- PHP 7.4+ (с расширением phpredis)
- Redis сервер
- Любой веб-сервер с поддержкой PHP (Apache/Nginx или USBWebServer/OpenServer)

React, Node.js, npm и сборка **не нужны** — это статические файлы + PHP.

### Установка

1. **Запустите Redis:**
```bash
redis-server
```

2. **Разместите файлы проекта в корне веб-сервера** (структура уже готова к раздаче, копировать никуда не нужно):
```
/                       ← корень веб-сервера (docroot)
├── game.html           ← игровой клиент (основная страница игры)
├── diag.html           ← страница диагностики окружения
├── css/game.css        ← стили клиента
├── js/                 ← клиент боевой системы, модули: config/state/utils/grid/
│                             path/animation/render/input/net/main (polling, рендер, ввод)
├── data/
│   ├── battledata.json       ← бойцы/объекты/ловушки/NPC + их комнаты старта
│   ├── A1.json  A5.json      ← карты комнат-углов (стартовые позиции бойцов)
│   ├── B1.json               ← центральная комната: бочки, мина, турель, 4 двери
│   └── E1.json  E5.json      ← карты остальных комнат-углов
├── tests/
│   └── harness_engine.php    ← CLI-харнесс сценарных тестов (in-memory фейк Redis)
└── php/
    ├── config.php            ← Redis-коннект, ключи (в т.ч. room:<ID>), JSON-хелперы, лог
    ├── init.php              ← эндпоинт инициализации боя
    ├── poll.php              ← long polling + серверный тик + snapshot комнаты игрока
    ├── action.php            ← POST-обработчик действий
    ├── battle.php            ← фасад обратной совместимости
    ├── debug.php             ← диагностика движка
    ├── engine/               ← ядро: rules, geometry, events (шина), world (Redis), turn, bootstrap
    └── systems/              ← механики: effects, combat, movement, passives, targeting,
                              │            abilities, objects, rooms (комнаты/двери/респаун)
```

3. **Откройте в браузере:**
```
http://localhost/game.html
```

4. **Для мультиплеера:** откройте game.html в нескольких вкладках, выберите разных персонажей.

### Диагностика

Если бой не запускается:
- `diag.html` — проверка доступности PHP-эндпоинтов из браузера;
- `php/debug.php` — проверка версии PHP, наличия расширения redis и подключения к Redis (выводит ошибки напрямую, без JSON).

### Настройка Redis

Отредактируйте `php/config.php`:
```php
define('REDIS_HOST', '127.0.0.1');
define('REDIS_PORT', 6379);
define('REDIS_DB', 0);
```

## Структура проекта

### PHP файлы (`php/`)

Архитектура двухслойная: тонкие HTTP-эндпоинты → движок `engine/` (ядро) + `systems/` (механики),
связанные событийной шиной. Подробно — в `ARCH.md`.

| Файл | Назначение |
|------|-----------|
| `config.php` | Только инфраструктура: подключение Redis, JSON-ответы, лог. Игровые константы перенесены в `engine/rules.php` |
| `init.php` | Сброс Redis (flushDB) и загрузка `data/battledata.json` + карт комнат (`data/<ROOM_ID>.json`: legacy-комната с сущностями и стартовые комнаты бойцов) в состояние боя (`world_init`); отдаёт клиенту реестры и серверные правила (`rules`) |
| `poll.php` | Long polling endpoint + серверный тик (`turn_tick`: движения, переходы/двери, смерть+респаун, снаряды, ход, NPC, тик эффектов). Snapshot отдаётся **по комнате запросившего игрока** (`?player=`): `room`, `room_id`, `grid` + только объекты/ловушки/NPC его комнаты |
| `action.php` | POST-обработчик действий: `move` / `attack` / `ability` (валидация живости/CC/AP → роутинг в системы; ошибки — JSON 400) |
| `battle.php` | Фасад обратной совместимости: legacy-имена функций (`processMove`, `checkVictory`, …) как делегаты в engine/systems. Новый код здесь не пишется |
| `engine/rules.php` | Единый источник констант мира (GRID 16×12, MOVE_SPEED, TURN_DURATION, SHIELD_REGEN_PER_TURN и др.) + формула TURN + payload правил для клиента |
| `engine/geometry.php` | Чистые функции координат: parseXY/formatXY/manhattan/calculatePath и т.п. |
| `engine/events.php` | Событийная шина: `hook()/emit()/emitReduce()` (query-события с мутацией по ссылке) |
| `engine/world.php` | Единственный владелец хранилища Redis (`battle:*`): world_load/save/init/log/version; инкремент версии централизован |
| `engine/turn.php` | Оркестратор тика хода: движение → смерть → снаряды → NPC → тик эффектов; новый ход каждые TURN_DURATION сек |
| `engine/bootstrap.php` | Точка сборки: подключение систем + регистрация слушателей шины в фиксированном порядке |
| `systems/effects.php` | Реестр статус-эффектов (STUNNED, BLEED, FROZEN…): длительность `[N]` ходов, DoT, CC-блокировки |
| `systems/combat.php` | Единая цепочка урона: сопротивление/пробитие → щит → HP → смерть; атаки игроков |
| `systems/movement.php` | Движение: предсказание на копии vs серверное применение, модификаторы дальности/блокировки |
| `systems/passives.php` | Реестр пассивок как слушатели шины (REGENERATION, ARMORED, ARMOR_CRUSH, SPLASH, THORNS, SWIFT/SLOWED, PUNCTURE) |
| `systems/targeting.php` | Универсальный доступ к сущностям и выбор целей (AoE бьёт игроков, NPC, объекты) |
| `systems/abilities.php` | Реестр способностей и их применение (instant/beam/line/area) через сервисы combat/effects |
| `systems/objects.php` | Автономные объекты: NPC (зоны угрозы, LOS **внутри своей комнаты**, ИИ-атака раз в ход, не стреляет по мёртвым) и ловушки (срабатывание по ALLY) |
| `systems/rooms.php` | Мультикомнатный мир: ленивая загрузка карт `data/<ID>.json` в `state['rooms']`, проверка проходимости клетки комнаты, подбор ближайшей свободной клетки у двери, `rooms_teleport()` (переход через дверь и респаун в личную `SPAWN_ROOM`), триггер дверей `rooms_check_exit_trigger()`, событие шины `room.changed` |
| `debug.php` | Отладочная страница: PHP, Redis, наличие/загрузка модулей движка, реестры, тест цикла (⚠️ делает flushDB) |

### Фронтенд

- `game.html` + `js/*.js` (модули клиента) + `css/game.css` — клиент игры: выбор персонажа, вызов `init.php`, цикл `poll.php?v=N&player=ID`, отправка действий в `action.php`, отрисовка сетки, анимации движения/снарядов/смерти, UI (HP/щит/ACTIONS, способности, лог).
- `diag.html` — диагностика.

### Данные (`data/`)

- `battledata.json` — 4 тестовых персонажа (PLAYER1–PLAYER4) с полями `ROOM_ID` / `SPAWN_ROOM` и личными стартовыми клетками, объекты (бочки), ловушка (мина), NPC (турель) — все сущности тоже привязаны к комнате полем `ROOM_ID`
- Комнатные карты (`A1.json`, `A5.json`, `B1.json`, `E1.json`, `E5.json`) — единый формат: `room_id`, `width`, `height`, `grid` (маска 0/1), `exits` («x,y» → КУДА), `exit_rooms` («x,y» → ОТКУДА, обратная дверь), `exit_positions` (клетка появления со стороны двери), `stairs` (пусто — вертикальные переходы не реализованы)
- **B1** — центральный зал 16×12: вертикальная стена в столбце 7 (кроме крайних рядов 0 и 11) и четыре двери по углам: `0,0 → A1`, `15,0 → A5`, `0,11 → E1`, `15,11 → E5`; в нём стоят бочки (`5,5`, `10,5`), мина (`5,8`) и турель (`8,3`)
- **A1 / A5 / E1 / E5** — открытые комнаты-угла (без стен) со стартовыми клетками бойцов рядом с дверью в B1: A1 `1,1`, A5 `14,1`, E1 `1,10`, E5 `14,10`

## Концепция и происхождение проекта

Проект вырос из задачи сделать **изолированный тестовый стенд боевой системы** для будущей браузерной игры (2D-платформер с локациями-«этажами»): меню, лобби, арсенал и локации планировались отдельно, здесь разрабатывался только «движок боя/передвижения».

Жёсткие принципы, заданные концептом и сохранённые в коде:
- **Только PHP + HTML/CSS/vanilla JS.** Никакого React/Node.js — ни в рантайме, ни в сборке. Фронтенд — обёртка для графики, вся игровая логика и расчёты — на сервере (PHP).
- Запуск «на коленке»: папка в usbwebserver/OpenServer + Redis, без сторонних движков и сборки.
- Состояние боя — в Redis, обмен между игроками — через long polling.
- Стартовые характеристики/экипировка/способности читаются из `data/battledata.json` (система экипировки намеренно не реализована — предметы «прописаны» заранее).
- Персонажи — цветные квадраты с ником и «словом» анимации (IDLE/MOVE/ATTACK/ABILITY/DEATH...); снаряды/лучи — контейнеры с фазами cast/hit.
- Локация — сетка 16×12; клетка содержит игрока, объект (разрушаемый/интерактивный), NPC или ловушку; невидимые препятствия — маска 0/1 в `data/<ROOM_ID>.json` с обозначением переходов.
- Способности и пассивки — реестры кода в `php/systems/` (abilities, passives, objects); предметы как данные — точка расширения.

Отличия текущей реализации от первоначального концепта (осознанные изменения в ходе разработки):
- Ход (восстановление ACTIONS): было «каждые 10 секунд» → стало `TURN_DURATION = 5` сек.
- Дальность способностей задаётся явно в реестре `systems/abilities.php` (`range`), а не только парсится из строки `ABILITY[N]` в battledata.json.
- В изначальном описании персонажам PLAYER1–PLAYER3 соответствовали пассивки REGENERATION/ARMORED/SPLASH — сейчас набор пассивок пересмотрен по тестовым данным (см. раздел «Тестовые персонажи»).
- Появились механики сверх старовой ТЗ: зоны угрозы NPC, прерывание движения уроном, баффы (FORTIFY/WAR CRY), мультикомнатный мир с дверями (`ROOM_ID`, `exits`), возрождение в личной комнате спавна (`LIFE`, `SPAWN_ROOM`).
- Часть фич концепта ещё не реализована: лестницы/«этажи» (вертикальные переходы — поле `stairs` пустует), из плановой сетки 5×5 построены только B1 и четыре угла, объекты взаимодействия (TERMINAL) — см. «План развития».

## Игровые механики

### Сетка и комнаты
- 16 столбцов × 12 строк (константы `GRID_WIDTH` / `GRID_HEIGHT`) — **размер единый для всех комнат**, координаты разных комнат перекрываются (клетка `5,5` живёт и в A1, и в B1). Отсюда главный инвариант: любое взаимодействие возможно только внутри одной комнаты (`ROOM_ID`)
- Комната **B1**: вертикальная стена в столбце 7 (кроме крайних рядов), четыре двери по углам — `0,0 ↔ A1`, `15,0 ↔ A5`, `0,11 ↔ E1`, `15,11 ↔ E5`. Двери **работают**: наступил на клетку exit → мгновенный переход в соседнюю комнату
- Комнаты **A1 / A5 / E1 / E5** — открытые угловые залы без стен, стартовые клетки бойцов рядом с дверью в B1
- Стены блокируют путь (0 в карте); проверка всегда идёт по карте комнаты бойца, стены соседних комнат не влияют

### Ход
- Каждые `TURN_DURATION` (5) секунд ACTIONS восстанавливаются до MAX_ACTIONS (без накопления «впрок»)
- Каждое действие (move/attack/ability) = 1 очко ACTIONS
- Кулдаунов на способности нет — только стоимость в очках действий; скобка `[N]` в названии способности — это её дальность, а не стоимость
- Действия обрабатываются в реальном времени, без очерёдности игроков

### Перемещение
- До `MAX_MOVE_DISTANCE` (5) клеток за 1 действие (+SWIFT, −2 при SLOWED)
- Только по прямой (вверх/вниз/влево/вправо), без автоогибания препятствий
- Нельзя проходить сквозь стены/игроков/живых NPC (турель — непроходимое препятствие, пока жива); нельзя стартовать с занятой клетки; клетка мёртвого игрока (DEATH/DECAY/REMOVED) свободна для других
- Во время движения сервер плавно обновляет позицию (`MOVE_SPEED` = 3 клетки/сек) и проверяет ловушки и зоны угрозы NPC на каждой пройденной клетке
- При старте движения путь только **предсказывается** на черновом копийстве состояния (`makeTrapPreviewState()`): ловушка/NPC заранее укорачивают конечную точку маршрута, но реальный урон и эффекты (STUNNED/DEATH) применяются в `movement_update()` ровно в тот момент, когда серверные часы доводят игрока до клетки мины. Так анимация на клиенте всегда «доезжает» до клетки срабатывания — рассинхрон (урон есть, а позиция ещё стартовая) исключён
- Вход на клетку мины **немедленно завершает движение**: CUR/START/END фиксируются на клетке ловушки, MOVE_* удаляются, STATUS становится STUNNED (или DEATH при летальном уроне) без ожидания следующего хода; если оглушение получено на промежуточной клетке, статус MOVING сохраняется до конца пути, а STUNNED восстанавливается на финале
- Получение урона прерывает перемещение — игрок останавливается на последней достигнутой клетке
- Во время MOVING недоступны другие действия (move/attack/ability блокируются сервером)

### Направление спрайта (TURN)
- Поле `TURN` хранит направление «взгляда» персонажа: только `LEFT` или `RIGHT` (в battledata.json задаётся стартовым, дальше управляется сервером)
- Горизонтальное перемещение, атака или применение способности переписывают TURN (влево ⇒ LEFT, вправо ⇒ RIGHT); вертикальные действия и самоприменение направление НЕ меняют
- Клиент зеркалит div персонажа по горизонтали (`scaleX(-1)`, класс `turn-left` в js/game.js + css/game.css), включая середину пути: анимация движения сохраняет отражение внутри inline transform
- Поворот при Attack/Ability применяется мгновенно (`previewTurn()` в js/game.js — та же формула, что на сервере `rules_turn_formula()`), не дожидаясь long-poll ответа с обновлённым TURN; статус ABILITY возвращается в IDLE через 1 сек так же, как ATTACK (сброс — `turn_reset_attack_status()` в php/engine/turn.php)
- Статусные CSS-анимации: attack-flash и ability-glow используют только filter/box-shadow (перемножаются с scaleX отражения автоматически); idle-bounce/stun-shake имеют flipped-варианты keyframes; death/decay — простые 1-секундные циклы без opacity/scale-эффектов, отражаются через `--turn-flip`. Правило для новых keyframes со transform: либо только filter, либо домножение на `scaleX(var(--turn-flip))`, иначе они перекроют отражение
- Смерть проигрывается полностью: DEATH (1 сек) → DECAY (1 сек) → исчезновение с поля. Сервер переводит статусы и выполняет респавн/REMOVED только после окончания обеих стадий; клиент убирает div из DOM лишь при STATUS=REMOVED (во время DEATH/DECAY блок остаётся на клетке и отрисовывает анимации, включая корректный TURN). При этом уже со статуса DEATH сервер считает клетку мёртвого игрока свободной — другие игроки могут по ней ходить
- На геймплей (спина/фланг) TURN пока не влияет — это только визуальная механика

### Ввод (клиент)
- Клик по клетке не выполняет действие сразу — открывается диалог доступных действий: «Переместить», «Атаковать», кнопки Способность 1–3 (отображаются только если цель в зоне дальности способности)

### Атака
- В пределах RANGE (для BLINDED — RANGE/2)
- Формула урона (единая цепочка `combat_apply_damage`, helper-функция `calculateDamage`): `ceil(max(ATTACK, 1) × (1 − RESISTANCE×10%))`, сопротивление макс. 90%, минимум 1 урон
- Урон сначала списывает SHIELD, затем HITPOINTS; при смерти — цепочка DEATH (1 сек) → DECAY (1 сек) → **респаун через `rooms_teleport(..., 'respawn')` в личную `SPAWN_ROOM`** на свою `START_POSITION_XY` (если она свободна) либо на ближайшую свободную клетку у двери этой комнаты. Если телепорт невозможен (нет карты/свободной клетки) — страховочный возврат на `START_POSITION_XY` внутри текущей комнаты; если `SPAWN_ROOM` не задана — остаёмся там, где умерли. При исчерпанных `LIFE` — STATUS=REMOVED

### Способности
- 4 механизма применения: instant (без снаряда, BACKSTAB/SHIELD BASH/FORTIFY), beam (точечный луч), line (линия, задевает всех на пути), area (область по радиусу AoE)
- Типы урона: physical / fire / ice / poison
- Могут накладывать негативные эффекты, а также баффы: self_buff (FORTIFY — +3 щита), ally_buff (WAR CRY — +2 ATK союзникам в области)
- Все снаряды создаются в состоянии и визуализируются клиентом

### Пассивки
| Название | Эффект |
|----------|--------|
| REGENERATION | +1 HP/ход |
| ARMORED | снижает входящий урон вдвое, но только от атак с флагом пробития сопротивления (`pierce` — атаки носителей ARMOR_CRUSH; на обычные атаки и NPC не действует) |
| ARMOR_CRUSH | атаки носителя игнорируют всё сопротивление цели (RESISTANCE и ARMORED); не работает, если у носителя есть ARMORED (взаимоисключающая синергия) |
| SPLASH | 1 урон соседним врагам при атаке |
| THORNS | 1 урон атакующему при получении урона |
| SWIFT | +1 к дальности перемещения |
| PUNCTURE | атака пробивает всех врагов на пути до цели |

NPC-урон (турель/мина) идёт по единой цепочке без сопротивления цели — одинаковый по всем целям.

### Негативные эффекты
| Эффект | Действие |
|--------|----------|
| FROZEN[N] | -1 ACTION каждый ход, N ходов |
| POISONED[N] | -1 HP/ход, N ходов |
| BLEED[N] | -1 HP/ход, N ходов |
| STUNNED[N] | 0 ACTIONS, N ходов |
| SLOWED[N] | -2 к дальности перемещения, N ходов |
| BLINDED[N] | дальность атаки/способностей /2, N ходов |

### Объекты, ловушки и NPC
- **Объекты** (бочки, `objects`): имеют HP, разрушаются от урона, блокируют клетки
- **Ловушки** (`traps`): мина MINE1 — при входе на клетку наносит урон и накладывает эффекты (STUNNED[2], BLEED[2]) по радиусу RANGE; игрок мгновенно останавливается на клетке мины, STUNNED активируется сразу (`effects_apply` + слушатель `effect.applied`), а не на следующем ходе
- **NPC** (`npcs`, логика в `php/systems/objects.php`): турель TURRET1 — «зоны угрозы» (`calculateThreatZone` / `objects_check_threat_zone`): вход игрока (в т.ч. во время движения) в зону провоцирует NPC на выстрел; при выстреле NPC переходит в STATUS = 'ATTACK' (анимация), сброс в IDLE — `objects_update_npc_statuses()` каждый тик (`turn_tick`). Живой NPC также блокирует свою клетку как препятствие (`is_cell_passable()` в `php/systems/targeting.php`): пройти сквозь него или занять его клетку нельзя, после уничтожения клетка освобождается

## Расширение

### Добавить способность
1. Добавьте определение в `systems/abilities.php` → `getAbilityDefinitions()`
2. Добавьте в ABILITIES игрока в `battledata.json`
3. Урон/эффекты — только через сервисы `combat_apply_damage()` / `effects_apply()`

### Добавить статус-эффект (DOT/CC)
1. Только реестр в `systems/effects.php` (kind: dot/cc/modifier, длительность, модификаторы)
2. Блокировки действий берутся автоматически через `effects_blocks()`, тик — через `effects_tick()`

### Добавить пассивку
1. Добавьте определение в `systems/passives.php` → `getPassiveDefinitions()`
2. Добавьте слушатель шины в `passives_register_hooks()`: `turn.start` (реген-подобные),
   `damage.query_mitigate` (защитные), `damage.dealt` (откормка), `attack.resolved` (сплэш),
   `movement.query_distance` (модификаторы движения)
3. Добавьте в PASSIVES игрока в `battledata.json`

### Добавить комнату
1. Создайте `data/ROOM_ID.json` по формату соседних карт: `room_id`, `width`, `height`,
   `grid`, `exits` («x,y» → КУДА), `exit_rooms` (обратная дверь), `exit_positions`, `stairs`
2. Пропишите в этой карте встречные двери в соседние комнаты и **обязательно** обратные
   записи `exit_rooms` у соседей — иначе входящий появится не у «своей» двери
3. Код править не нужно: карта подхватится лениво (`room_get()`), переход выполняет
   `rooms_teleport()`, триггер двери — `rooms_check_exit_trigger()` в финале движения
4. Чтобы заселить комнату, добавьте сущностям/игрокам в `battledata.json` поле `ROOM_ID`
   (для бойцов ещё и `SPAWN_ROOM`) — комната автоматически попадёт в стартовый набор Redis

### Добавить NPC
1. Добавьте в `npcs` в `battledata.json`
2. AI и зоны угрозы обрабатываются в `systems/objects.php` (слушатель `turn.start`,
   `calculateThreatZone` / пересечение зон при движении)

### Добавить автономный объект (ловушку/будущий spawn-объект от способности)
1. Логика всех автономных объектов — только в `systems/objects.php`
2. Добавьте тип объекта в `getAutonomousObjectDefinitions()` (`systems/objects.php`)
3. Не забудьте поле `ALLY`: игрок-создатель и его союзник не должны восприниматься объектом как враги

## API и синхронизация (Long Polling)

### Эндпоинты

| Эндпоинт | Метод | Описание |
|----------|-------|----------|
| `php/init.php` | GET | Сброс и инициализация боя из `data/*.json` (вызывается при входе первого игрока) |
| `php/poll.php?v=VERSION&player=ID` | GET | Долгое ожидание изменений состояния + серверный тик |
| `php/action.php` | POST (JSON) | Действия: `{"action":"move","player":"PLAYER1","x":3,"y":5}`, аналогично `attack`, для `ability` поле `"ability":"FIRE WAVE"` |
| `php/debug.php` | GET | Диагностика PHP/Redis |

### Как работает polling

Клиент запрашивает `poll.php?v=VERSION&player=PLAYER_ID`, сервер держит соединение до:
- Появления новой версии (любое успешное действие или начало нового хода инкрементируют `battle:version`)
- Истечения таймаута (`LONG_POLL_TIMEOUT` = 25 секунд)

Каждый цикл poll на сервере выполняет тик:
1. `turn_tick($state)` выполняется для **любого** запроса (даже без `player`): движение по
   серверным часам (+ триггер дверей в финале движения → `rooms_teleport`) → анимации смерти
   и респаун в личной `SPAWN_ROOM` → снаряды → сброс ATTACK у NPC → тик статус-эффектов
   (длящиеся `[N]` ходов реально снимаются);
2. Если прошло `TURN_DURATION` (5) сек — новый ход: `turn_start()` + событие `turn.start`
   (слушатели: реген щита/HP, негативы/DoT, восстановление ACTIONS игроков и NPC, зоны угрозы),
   версия инкрементируется;
3. Если версия выросла — snapshot отправляется клиенту (flat JSON, без обёртки `data`).

Snapshot **комнатно-изолирован**: при запросе с `?player=` сервер отдаёт карту комнаты этого
бойца (`room`, `room_id`, `grid`) и только те объекты/ловушки/NPC, чей `ROOM_ID` совпадает с
его комнатой; игроки отдаются все (с полем `ROOM_ID`), а клиент сам рисует лишь соседей по
комнате. Без `?player=` используется legacy-карта `state['room']`.

Состояние лежит в Redis под префиксом `battle:`: `players`, `objects`, `traps`, `npcs`,
`projectiles`, `turn_time`, `version`, `log`, `action_acks`, `world_move_now` (виртуальные часы
движения, обновляется без инкремента версии), плюс мультикомнатный слой — `room` (legacy-карта
единой комнаты) и `room:list` + `room:<ID>` (JSON-карты только реально «оседлавших» мир комнат;
остальные грузятся лениво из `data/<ID>.json`). Доступ к хранилищу — только через
`engine/world.php` (`world_save()` сам инкрементирует версию). Клиенту в snapshot отдаются
последние 30 записей лога (в Redis хранится буфер из 50).
